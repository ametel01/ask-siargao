# Database Authorization Reference

Production Postgres access is split by operational role. The web runtime should not connect as the
schema owner, and migration credentials should not be reused by request handlers.

## Roles

| Role | Purpose | Login posture |
| --- | --- | --- |
| `ask_siargao_migration` | Owns the `public` schema objects, applies SQL migrations, and writes `schema_migrations` ledger rows. | Use only for `bun run db:migrate` and controlled schema operations. |
| `ask_siargao_runtime` | Reads and writes application tables after migrations are complete. | Use for the deployed app and app-owned jobs that need normal DML. |
| `ask_siargao_reporting` | Reads approved reporting tables. | Optional; create separate login credentials for BI/reporting tools when needed. |

Create provider login roles separately, grant each login to the matching group role, and store those
credentials in the provider secret store. Do not expose any database URL through a
`NEXT_PUBLIC_` environment variable.

## SQL Template

The canonical provider-neutral grant template is generated by
`src/server/db/authorization-boundaries.ts` and covered by
`src/server/db/authorization-boundaries.test.ts`.

From the repository root, print the default template with:

```sh
bun -e 'import { buildDatabaseAuthorizationSql } from "./src/server/db/authorization-boundaries"; console.log(buildDatabaseAuthorizationSql())'
```

Use custom identifiers when a provider requires different names:

```sh
bun -e 'import { buildDatabaseAuthorizationSql } from "./src/server/db/authorization-boundaries"; console.log(buildDatabaseAuthorizationSql({ databaseName: "ask_siargao_prod", migrationRole: "asi_prod_migration", runtimeRole: "asi_prod_runtime", reportingRole: "asi_prod_reporting" }))'
```

The template:

- creates separate non-login group roles for migration, runtime, and reporting access;
- revokes broad `PUBLIC` database, schema, table, and sequence privileges;
- grants schema `CREATE` only to the migration role;
- transfers current application tables and `schema_migrations` ownership to the migration role;
- grants runtime `SELECT`, `INSERT`, `UPDATE`, and `DELETE` only on application tables, not on
  `schema_migrations`;
- grants reporting `SELECT` only on the approved reporting table set;
- grants sequence usage needed by runtime and read-only sequence access needed by reporting;
- sets migration-role default privileges so future objects do not regain broad `PUBLIC` access.

Run the generated SQL as the provider bootstrap owner after migrations have created the current
schema. For later migrations, connect with the migration credential so new tables inherit the
documented default privileges.

## Runtime Credential

Set the deployed app's `DATABASE_URL` to a login role that is a member of
`ask_siargao_runtime`. This credential can run normal application reads and writes, but it should
not own schema objects and should not be able to write `schema_migrations`.

Do not run `bun run db:migrate` with the runtime credential. The migration runner needs the
migration credential because it creates and alters schema objects, takes the advisory lock, and
records checksums in `schema_migrations`.

## Migration Credential

Use a login role that is a member of `ask_siargao_migration` for:

- `bun run db:migrate`;
- controlled schema repair supervised by an operator;
- applying future migration files from `drizzle/`.

The migration role is intentionally powerful because Postgres requires table ownership or owner
membership for many `ALTER TABLE` operations. Keep the credential out of the runtime environment
except during migration jobs.

## Reporting Credential

The default reporting table set excludes user-owned chat, profile, saved-trip, payment, and audit
tables. It is meant for public knowledge, source, and operational reporting where read-only access is
acceptable.

If a reporting tool needs private or paid-flow tables, create a separate reviewed grant set for that
tool instead of broadening the default `ask_siargao_reporting` template.

## RLS Boundary

User-owned tables are listed in `userOwnedTables` in
`src/server/db/authorization-boundaries.ts`. Row-level security is not enabled by this template.
The current decision and activation prerequisites are documented in
[`database-row-level-security-decision.md`](../explanation/database-row-level-security-decision.md).
